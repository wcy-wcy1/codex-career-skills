# 按回答选择追问路径

以下是选题地图，不是顺序必问清单。每轮只提出其中一个聚焦问题；按用户回答继续，通常不在同一主问题追问超过两次。临时改为专项深挖时说明范围。

## 开场选择

- 已有简历：从目标岗位最相关的主项目开始，例如“这个项目的主要使用者最需要解决什么问题？”
- 无简历但方向明确：“请简要介绍一个最能代表你目前能力的项目。”后续再补业务、贡献等信息，不一次抛完整问卷。
- 用户指定某技术：先核对实际使用范围，再进入场景题；不擅自改回完整综合面试。

## 通用项目路径

| 触发信号 | 下一问可选择 | 观察重点 |
| --- | --- | --- |
| 只有功能名 | “谁在什么步骤会用到它？” | 明确业务任务，工具/科研/个人用户都可成立 |
| 只说“我们做了” | “其中你独立完成的一个模块是什么？” | 归属、个人动作，避免把没主导当没贡献 |
| 列很多框架 | “一次请求怎样经过这些组件得到结果？” | 数据流、组件职责、实际实现 |
| 只说“效果更好” | “你用什么依据判断它比改动前好？” | 基线、样本、指标或可复现验证 |
| 只说接入 API | “这个接入中你实际处理过的一个限制是什么？” | 超时、费用、格式或质量等真实约束，而非贬低 API 项目 |
| 说做了版本迭代 | “哪一个具体问题触发了这次改动？” | 不编用户反馈，接受测试、失败样例或实验依据 |
| 声称做了优化 | “如果移除这项优化，会出现什么变化？” | 理解因果与适用边界，区分测量和猜测 |
| 有自相矛盾 | “刚才提到 A，现在说 B，这两种情况分别适用于哪里？” | 先澄清阶段或范围，再判断问题 |

## 大模型应用岗位

根据 JD 与项目选相关分支，不要求每人全会：

- **RAG**：数据进入系统与检索链路；分块和检索的取舍；召回差还是生成差如何区分；重排或 Query 改写何时有帮助。选择一个失败样例追问定位依据。
- **Agent / 工具调用**：为何需要工具或多步执行；状态与终止条件；工具失败、重复调用及权限边界。不要预设所有项目必须多 Agent。
- **模型服务与后端**：超时、限流、重试、降级、流式响应、费用与时延。问候选人实际处理的约束；重复执行有副作用时再考察幂等。
- **评测与观测**：基线、样本、质量指标、失败分类、成本或时延口径；确认改动带来的收益和代价。没有线上数据可用离线评测，不能把离线分数说成线上业务收益。
- **多模态或微调**：仅在 JD 或项目相关时问数据、选择理由、评测与成本，不以是否微调作为应用开发统一门槛。

## 后端及基础设施

- **Redis**：先问缓存什么、为什么、TTL 与一致性要求；依据场景再选穿透/击穿/雪崩、淘汰策略、热点 Key 或高可用。使用 Redis 不代表必须掌握全部机制。
- **ES / 检索**：索引、查询和数据更新如何服务该业务；根据实际使用再问分词、排序或并发控制，不把所有底层实现变成统一背诵题。
- **接口可靠性**：先明确操作是否有副作用，再问重复请求、超时重试或事务边界；不要把 REST 风格与幂等保障混为一谈。
- **追踪与日志**：候选人说记录 trace ID 时，先问怎样传播和使用；自定义日志关联也可能合理。不预设装了 SkyWalking，也不因没装特定产品判错。

## 行为题与协作

选择真实分歧、失败或计划调整，沿“背景—本人责任—动作—结果与反思”追问。没有工作经验可以用个人项目、课程或开源协作。不能替用户编领导团队、线上事故或商业成绩。

## 知识边界与严格模式

问题要可回答、与目标相关，不能故意塞错误前提。专业事实不确定时先核对可靠资料再评价；无法核实则标注该结论待核实，不用自信语气判错。严格模式检索资料时不提前把答案展示给用户；用户要求讲解后再提供。

已达到本次约定数量或用户说结束时，停止追问并读评分参考生成复盘；用户只答了一题也能做局部复盘，但保持其余维度未评估。
