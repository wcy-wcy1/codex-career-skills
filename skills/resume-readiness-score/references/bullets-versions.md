# Bullet、量化、版本与缺口转任务

## Bullet 改写

按事实选择一种结构，不要求每条都套同一个公式：

- **技术成果**：动作 + 技术对象/机制 + 解决的问题 + 结果或验证。
- **X-Y-Z**：完成了什么 X，由什么 Y 衡量，通过什么 Z 实现。
- **STAR/CAR 压缩**：背景/挑战 + 本人动作 + 结果，适合项目或实习主线。

弱句通常只有“负责、参与、协助、使用了”。改写时优先补：

1. 本人动作（设计、实现、调试、评测、部署、协作的具体范围）；
2. 技术对象（接口、检索链路、数据管道、模型调用、缓存等）；
3. 问题或约束（延迟、重复提交、召回质量、成本、格式、可靠性）；
4. 结果与验证（指标、规模、测试样本、运行记录或明确的定性结果）。

一个 Bullet 只承载一个主要成果，通常控制在一到两行。不要把整个架构图、依赖列表或所有技术名词塞进 Bullet。

## 量化证据阶梯

优先级从高到低：

1. 用户确认的准确指标，带基线、样本、环境或时间范围；
2. 用户确认的范围或区间；
3. 可核对的规模/输入，例如请求量、数据量、项目数量、测试样本、处理时长；
4. 可复现的验证方式，例如压测、离线评测、回归测试、演示记录；
5. 没有数字时的准确定性结果与已知限制。

不要为了“每条有数字”估一个好看的提升比例。若用户提供的是估算值，保留“约/范围/估算”及依据；若没有依据，不把建议指标写进投递稿。

## 技术岗位结构与栏目

技术岗位可按证据选择：联系方式、Summary（必要时）、Technical Skills、Experience、Projects、Education、Certifications/Links。技能按真实使用和目标 JD 分类，不用水平条，不把软技能孤立列成关键词。GitHub、作品集或 README 只有在链接可用且能支持主张时才加入。

项目格式建议包含：项目名、状态/来源、技术栈、简短任务背景、个人动作、关键设计、结果/验证和链接（如有）。个人项目、课程、科研和开源贡献可以保留，但必须准确标明来源和贡献边界。

## Master 与投递版本

- **Master Resume** 是事实源：保存完整经历、候选 Bullet、项目事实卡、技能范围和证据位置。
- **岗位版本** 从 Master 复制，按目标 JD 重排、改写和精简；不要直接修改 Master。
- **公司版本** 记录公司、岗位、JD 日期、文件名、关键词变化、提交日期和状态；面试后把新事实先核实，再回写 Master。
- 推荐文件名：`姓名_岗位_公司_YYYYMMDD.pdf`；Master 可用 `姓名_Master_Resume_YYYYMMDD.docx`。
- 旧版本归档而非覆盖删除；没有投递记录时不能声称某公司收到的是哪一版。

## 缺口转项目任务

当用户授权补项目或提升证据时，用以下映射：

```text
简历缺口 → 目标能力 → 最小业务闭环 → 实现/验证任务 → 证据产物 → 可写入的简历句 → 面试追问
```

例：项目没有业务闭环，可拆成“确定使用者和输入输出、完成一次可运行流程、加入一个真实限制、做一项测试或离线评测、记录结果和边界”。完成教程、安装框架或跑通 Demo 不自动等于完成岗位能力，也不自动成为简历成果。

实现任务必须单列状态：未开始、开发中、已运行、已验证、候选人能解释。只有后两项才可作为已完成投递证据；计划和目标稿要显著标记。

## 交接到模拟面试

为每个岗位版本保留：简历关键主张、事实来源、技能范围、未验证点、项目主线、可能追问和使用版本。交给模拟面试技能时，先验证该版本的主张；不要用 Master 里未放入投递稿的内容替代面试官看到的简历。
