# 事实采集、简历正文与交接

## 主项目事实卡

只补缺项，不把整张表当作必须让用户一次填完的问卷。

| 字段 | 要收集的事实 |
| --- | --- |
| 来源与阶段 | 实习/工作/课程/个人/开源改造；进行中、演示、试用或生产使用 |
| 使用方与问题 | 谁在什么流程遇到什么问题，现有做法哪里不足 |
| 输入输出与验收 | 输入的数据或请求、输出动作或结果、判断有效的方式 |
| 个人职责 | 自己实现、改造、测试、部署的范围；团队或上游提供的部分 |
| 技术方案 | 关键组件、数据流、选型原因；别把整套依赖列表搬进简历 |
| 问题与改进 | 真实故障/限制/测试反馈、诊断依据、改动原因和后续结果 |
| 验证与限制 | 样例、运行记录、评测/压测或用户反馈；适用范围和未解决问题 |
| 事实来源 | 用户陈述、简历原句、代码/报告位置等；来源不足只标待确认 |

没有商业客户可以有明确目标用户；没有上线可以有离线评测；没有多次迭代可以如实写当前版本及一次调试过程。不能把计划当完成。

## 简历写法

推荐骨架按材料调整，避免强制三项目或固定一页：

1. 基本信息、目标岗位、教育背景。
2. 技能：按岗位相关能力组织，写范围与可追问内容。
3. 工作/实习：公司、时间、角色和实际交付。
4. 项目：简要业务背景、核心技术栈、个人动作与结果。
5. 相关科研、竞赛、开源等补充证据。

经历条目的结构：**为谁解决什么问题 + 我做了什么关键设计/实现 + 已知结果及边界**。必要时拆成两句，不把一条写成技术长名单。

技能条目的结构：**技术/能力 + 实际掌握机制 + 使用场景或动作**。只有“了解”但未使用的内容可明确写学习范围；不伪装成熟工程经验。

下面是写法示例，不是候选人的事实，不可直接复制到其简历：

```text
弱：熟悉 Redis，熟悉接口设计，做过大模型项目。
有事实才可写：在异步任务接口中使用 Redis 保存任务状态，设置过期时间清理历史记录；为重复提交增加请求标识校验。
```

不要把“使用过 Redis”扩写成“熟悉高可用、热点 Key、延迟双删”。不要从“记录 trace ID”推断接入 SkyWalking；应用日志关联也应按原样表述。

结果有数字时核对：指标定义、基线、样本、环境、时间区间、测量方法、是否本人贡献。缺数字可准确写交付能力和验证方式；不得估一个好看的提升比例。

## 修改交付表

| 原句/缺失位置 | 具体问题 | 可直接使用的改写 | 尚缺事实 | 验收动作 |
| --- | --- | --- | --- | --- |
| 引用用户材料 | 只写有证据的问题 | 只使用当前事实 | 分清待确认与待实现 | 能用哪个材料或回答验证 |

只有草稿允许明确的“待补：……”占位；投递版本应删除占位及未完成主张，并把遗漏放在单独清单。若用户主动要目标稿，显著标记“待实现目标稿”，保留任务到目标条目的映射。

## 面试交接卡

可交给模拟面试技能，也可独立用于自练：

```text
目标岗位/级别：
评价基线：具体 JD / 岗位方向
主项目及状态：
本人贡献与团队边界：
简历关键主张：
事实来源与未核实部分：
技术机制、选型与失败场景：
结果口径与已知限制：
待验证问题：
```

优先从关键主张生成追问，不把技能词典全部转成必背题。简历评分与面试评分分别报告。
