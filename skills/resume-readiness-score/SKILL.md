# 简历制作与证据评分

把“做过什么”变成招聘者能理解、候选人能解释的经历。交付可用正文、可追溯评分和具体补齐任务，不能只有建议。默认中文，跟随用户语言与目标岗位。

## 接续材料与选择模式

- 复用会话里的目标岗位、JD、简历和项目资料。只问影响结果的缺失信息，不重复索取已有材料。
- 用户只要评分，就诊断并评分；只要制作，就先写正文并做简短自查；要求制作加打分，则先评已有材料、改写，再说明哪些评分确实改变。没有旧简历时不编造“修改前分数”。
- 没有 JD 时可按明确的岗位方向制作通用版，标为“岗位方向基线”；不宣称与某公司匹配。只有 JD、没有候选人经历时，给结构与事实采集问题，不能生成虚构履历或候选人分数。
- 按请求选择模式：`evidence-score`（经验证据评分）、`jd-tailor`（岗位定制）、`bullet-rewrite`（项目/经历句改写）、`ats-check`（解析与格式门禁）、`version-plan`（Master 与投递版本）。用户没有指定时，先完成经验证据评分，再询问或按上下文选择附加模式。
- 制作或改写时读 [事实卡与正文约定](references/evidence-templates.md)；经验证据评分读 [评分与必过点](references/rubric.md)；需要 JD/ATS/定制时读 [ATS 与岗位定制](references/ats-tailoring.md)；需要改句、量化、版本或补项目任务时读 [Bullet、量化与版本](references/bullets-versions.md)。

## 制作与审查流程

1. **确认评价对象**：岗位、级别、简历版本和材料范围。岗位明确的硬性资格单列核对，不揉入技术水平分。
2. **整理事实**：区分用户明确陈述、材料可支持、待澄清、计划实现。用户陈述可以作为简历依据，不要求每段经历都有代码或公司证明；不过不能声称已独立核实。
3. **对齐招聘要求**：将 JD 的核心职责映射到经历，区分硬性要求、重要要求和加分项，找出业务、贡献、技术方案、验证结果的缺口。后端、科研、竞赛、工具类经历是否保留取决于相关性与证据。
4. **写出正文**：说明服务对象与问题、个人动作、关键设计和实际结果。项目来源、职责、技术栈、状态要清楚；详细架构与故事放准备材料，避免把检查项机械塞成关键词长串。按 JD 调整 Summary、技能顺序、经历顺序和 Bullet 顺序，但只重排和改写真实信息。
5. **做专项审查**：需要时运行 ATS 解析/格式检查、关键词匹配、岗位定制、Bullet 改写和版本检查。专项分数与经验证据分分开，不能用关键词数量弥补项目证据不足。
6. **审查并打分**：每项扣分引用原句或具体缺失位置，给修改动作与验收条件。区分“写得不清楚”“尚无完成证据”“回答能力待验证”。
7. **给出下一步**：按影响排序，优先处理误导表述、主项目业务和贡献，再补技术解释、验证、JD 对齐和格式，最后处理排版细节。只有授权补项目时才进入实现。

## 必须保留的判断边界

- 不把个人项目改成公司交付，不补不存在的客户、上线、用户反馈、版本、职责或指标。学习目标写成单独的待实现清单，不能混入投递稿。
- 没写某技能不等于不会；写了也不证明会。只评简历时，“能否回答”保持待模拟验证。一次答不上来不能否定全部技能。
- 不要求人人掌握 Redis 全家桶、完整 RAG 链路或所有中间件。技能边界由 JD、真实项目和本人主张决定；“熟悉/了解”仍需要具体范围，不能仅换形容词遮掩空白。
- 业务价值可以是内部效率、研究复现、开发者工具或个人用户任务，不强制套金融、医疗、电商背景。没有线上用户时接受可复现演示、离线评测、压测或真实测试反馈。
- 无迭代时写当前版本及限制，可提出下一步验证；不能为了模板编三期版本。只有 trace ID 不自动意味着使用了完整分布式追踪组件，按实际实现描述。
- 不因学历或个人项目来源直接判不合格；不自动删除科研、竞赛、交换或后端经历。只删除无助于本次岗位、重复或挤占核心证据的内容。
- 老师录播提供了检查方向，不是统一招聘标准。不要沿用“所有校招暂停、全部转社招”或固定年份的策略；投递范围按当前招聘信息与候选人资格判断。
- ATS 关键词数量、关键词出现次数、页面长度和文件格式只能作为启发式信号。没有统一的“80% 就能过”或“每条 Bullet 必须有数字”的门槛；先保证事实、相关性和可解释性。
- 维护一个 Master Resume 作为事实源，再生成岗位/公司版本。定制版不得反向污染 Master；每个投递版本要记录岗位、日期、使用的版本和后续面试反馈。详见 [Bullet、量化与版本](references/bullets-versions.md)。

## 交付与复评

按请求规模给出：

- **简历正文**：制作时必交；待确认内容放正文之外，或明确标为不能直接投递的草稿占位。
- **评分表**：维度、权重、等级、得分、材料依据、缺口和通过条件；附覆盖率、评价基线和必过点状态。
- **专项结果**：按请求附经验证据分、JD 匹配分、ATS 兼容分和面试可解释度状态；默认不合成一个总分，以免格式或关键词掩盖真实证据缺口。
- **优先修复清单**：通常聚焦最影响结果的 3–5 项，注明是改表述、补事实、补实现还是准备追问。
- **面试交接卡**：主项目、关键主张、证据来源、待验证点和建议追问。只作为模拟面试输入，不代替面试成绩。
- **版本与投递记录**：需要版本管理时，列出 Master、目标岗位版本、文件名、改动摘要和使用状态。

复评沿用相同材料范围、岗位与权重，说明变化依据。仅润色文字不能抬高未验证的技术能力或捏造新成果。评分是内部准备量表，不是 ATS 官方分、面试通过率或录用概率。

用户要求文件时保留原稿，输出新版本；普通请求可直接在对话交付。制作 Word/PDF 时按环境里相应文档技能处理版式并检查渲染，缺少工具时提供可编辑正文并说明限制。不要为一次评分自动安装工具或开展公司研究。
